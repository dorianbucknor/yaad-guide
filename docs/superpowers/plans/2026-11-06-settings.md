# Account Settings Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A settings area (personal info, security, notification preferences, delete account) with a seven-day archive and restore, a daily permanent purge, and stored notification preferences.

**Architecture:** Two migrations (archive status and preferences table; account functions). Pure logic and zod schemas in `src/lib/settings/` and `src/lib/schemas/settings.ts` are shared by forms and server actions. The proxy learns an `archived` flag from the token. A cron route with the service-role client purges accounts archived more than seven days ago. UI is `/settings/*` plus `/auth/restore` and `/auth/archived`.

**Tech Stack:** Next.js 16.4 (Cache Components), Supabase (Postgres, RLS, Storage, pgTAP, Auth admin API), `@supabase/ssr`, react-hook-form + zod 4, shadcn on Base UI, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-06-settings-design.md` (binding). Builds on the auth-foundation and vendor-onboarding specs and the permissions work (`authorize()`).

## Global Constraints

- Every Supabase table has row-level security; never weaken it. New SQL goes in new migrations; applied migrations are never edited.
- Status, archive and restore are written only by security-definer functions (`set search_path = ''`, execute for `authenticated` only, revoked from `public, anon`); purge functions are `service_role` only.
- The service-role key (`SUPABASE_SERVICE_ROLE_KEY`) is read only in `src/lib/supabase/admin.ts`, used only by the purge route, never imported from client code, never committed; `.env.example` lists names only. `CRON_SECRET` protects the route.
- Every form uses react-hook-form with a zod schema; server actions validate with the same schema (`fromZod`, `ActionResult` from `src/lib/auth/result.ts`). Sensitive actions verify the user with `getUser()`.
- Components that read the session call `await connection()` first and render inside `<Suspense>` (pattern: `src/app/vendor/page.tsx`).
- Controls are at least 44px tall below `md` (use shared `src/components/ui`; add new primitives with the shadcn CLI). Sentence case, left aligned, labels above inputs, errors beside fields, status with icon and text, native date input (no shadcn Calendar), toasts use the button's own word ("Saved", "Signed out").
- UI tasks follow `DESIGN.md` and use the frontend-design and ui-ux-pro-max skills.
- Read `node_modules/next/dist/docs/` before relying on routing or caching behavior; `params` and `searchParams` are Promises.
- Commits end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`. Stage files by explicit path only; the working tree holds unrelated uncommitted landing-page work that must not be committed.

## Review Focus

1. An archived person reaching other pages or APIs with a stale token or by direct URL (Task 5).
2. The purge deleting the wrong or a restored account, or running without the secret or with the variable missing (Tasks 4 and 7).
3. Changing a password without proving the current one, and the Google-only path (Task 6).
4. Reading or writing another person's notification preferences, or switching off the locked row (Tasks 3 and 6).
5. Archive then restore leaving vendor profile statuses exactly as they were (Task 4).
6. The service-role key reaching a client bundle (Task 7).
7. Calling the delete action directly without typing DELETE or the password (Task 6).
